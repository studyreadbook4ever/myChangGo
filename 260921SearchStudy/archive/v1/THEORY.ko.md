# 검색 목적에서 출발해 토큰 임베딩을 직접 설계하기

이 실습의 질문은 **“관련 문서를 더 잘 찾게 하려면 어떤 토큰 벡터가 어떻게 바뀌어야 하는가?”**다.
임베딩 테이블을 무작위로 만들고, 검색 오차를 역전파해 그 테이블과 encoder를 함께 학습한다.
사전학습된 임베딩이나 BERT 가중치는 사용하지 않는다.

오늘 다루는 범위는 다음 흐름 전체다.

```text
검색 요구 → 학습 쌍 → vocabulary → 토큰 벡터 초기화
         → encoder → 문장 벡터 → 문서 점수 → 손실 → 각 가중치 갱신
```

완료 기준은 모델이 실행되는 것에 더해, **왜 특정 행에 gradient가 생겼는지 설명할 수 있는 것**이다.

## 1. 임베딩을 “만든다”는 일의 설계 단위

| 설계 대상 | 결정할 것 | 잘못 결정했을 때 |
|---|---|---|
| 검색 관련성 | 질의의 어떤 의도를 문서가 충족하는가 | 같은 주제라는 이유로 틀린 답을 가까이 배치 |
| 토큰화 | 단어·형태소·subword·문자 중 어떤 단위인가 | 미등록어 폭증, 과도한 길이, 정보 소실 |
| vocabulary | 어떤 데이터에서 어떤 항목을 채택하는가 | 평가 데이터 누출 또는 지나친 `[UNK]` |
| 입력 표현 | 임베딩 차원, 초기화, 위치 표현 | 표현 용량 부족, 위치 구분 불가 |
| encoder | 문맥·순서·역할을 어떻게 결합하는가 | 주어와 목적어가 바뀐 문장을 동일시 |
| 검색 표현 | pooling, 차원 축소, 정규화, 점수 | 학습 점수와 서비스 검색 점수가 불일치 |
| 학습 목적 | positive·negative와 loss 구성 | 진짜 정답을 밀어내는 false negative |

온톨로지 지식은 특히 첫 번째와 마지막 행에서 강력하다.
“인슐린은 약물이다”를 안다는 것과, “혈당을 낮추는 약은?”의 정답 문서를 정하는 것은 연결되지만 같은 작업은 아니다.

## 2. 토크나이저 학습과 임베딩 학습을 분리하기

토크나이저 학습은 문자열을 **어떤 조각과 ID로 표현할지** 정한다.
예를 들어 BPE의 merge 규칙이나 Unigram 모델의 조각 inventory를 학습한다.
임베딩 학습은 이미 정해진 ID에 대응하는 **실수 벡터를 어떤 값으로 바꿀지** 정한다.
일반적인 이산 토큰화에서는 검색 loss의 gradient가 토큰 ID 선택 과정을 거슬러 올라가 vocabulary를 변경하지 않는다.

주 검색 실습 `lab.py`는 공백 단위 토큰화와 명시적인 vocabulary를 사용한다.
이 경로에서는 BPE나 WordPiece를 학습하지 않는다. vocabulary 구성과 벡터 학습을 분리해서 관찰하기 위한 선택이다.
별도 `tokenizer_lab.py`에서는 BPE 토크나이저를 새로 학습한다. 여기서 만든 토크나이저가 주 검색 모델에 자동으로 연결되는 것은 아니다.
vocabulary에는 검색 대상 문서와 학습 질의만 사용한다. 검증 질의로 vocabulary를 늘리지 않는다.

검색 대상 문서가 처음부터 주어진 고정 corpus라면 그 문서들을 vocabulary 구성에 쓰는 것은 자연스럽다.
다만 이 설정이 검증하는 것은 **알려진 문서 집합에 대한 새로운 질의**다.
새 문서·새 entity·새 도메인까지 일반화했음을 보여주려면 별도 분할이 필요하다.

실제 한국어로 확장할 때는 다음 선택을 직접 비교한다.

| 선택 | 이점 | 비용·확인할 점 |
|---|---|---|
| 공백 단위 | 구현과 gradient 추적이 단순함 | `검색`, `검색을`, `검색에서`가 별도 항목 |
| 형태소 단위 | 조사·어미를 분리할 수 있음 | 분석 오류와 도메인 고유명사 처리 |
| subword | 미등록 표현을 알려진 조각으로 분해 | 조각 수 증가, entity 분절, tokenizer 의존성 |
| 문자·byte 단위 | 입력 표현 범위를 넓히기 쉬움 | 긴 시퀀스와 의미 조합 학습 비용 |

정규화 규칙도 모델의 일부다. 대소문자, 공백, Unicode, 숫자, 단위, 하이픈을 어떻게 처리할지 정한다.
`IL-6`와 `IL6`가 같은 entity인지, `10mg`와 `100mg`에서 숫자를 지워도 되는지 먼저 판단한다.
모든 표기를 정규화하면 편해 보이지만, 검색에 필요한 구별까지 없앨 수 있다.

`[UNK]`는 서로 다른 미등록 표현을 하나의 ID로 합친다.
다른 두 entity가 모두 `[UNK]`가 되면 encoder가 원래 표기를 복원할 근거는 사라진다.
미등록어 비율뿐 아니라 **질의에서 핵심 entity가 미등록어가 되는 비율**도 살펴야 한다.

`[PAD]`는 배치의 길이를 맞추는 기술적 기호다.
이번 실습에서는 해당 임베딩을 0으로 두고, attention과 pooling에서도 padding을 제외한다.
임베딩이 0이라는 사실만으로 충분하지 않다. 위치 벡터와 선형층 bias가 padding 위치를 다시 0이 아니게 만들 수 있다.

**체크포인트:** 검증 질의의 새 단어를 vocabulary에 추가하면 무엇이 바뀌는가?
답: 표현 가능한 입력의 범위가 달라진다. 그 행의 의미가 저절로 학습되는 것은 아니다.

## 3. 테이블의 초기값과 lookup의 실제 연산

vocabulary 크기를 `V`, 입력 차원을 `d=48`이라고 하자.
학습할 토큰 테이블은 `E ∈ R^(V×48)`이다. 각 원소를 평균 0, 표준편차 0.1인 정규분포로 초기화한다.
`[PAD]` 행은 별도로 0으로 설정한다. 0.1은 이번 작은 실험의 선택이며 보편적 최적값이 아니다.

무작위 초기화는 의미를 주입하지 않는다. 서로 다른 토큰을 구분 가능한 시작점에 놓는다.
최종 값은 학습 데이터, loss, encoder, optimizer가 함께 결정한다.
차원이 커지면 표현 용량과 파라미터 수 `V×d`가 늘지만, 부족한 감독 신호가 자동으로 보완되지는 않는다.

ID 시퀀스가 `i=[2, 5, 2]`라면 lookup은 다음과 같다.

```text
X = E[i] = [E[2], E[5], E[2]]       # [3, 48]
```

각 ID를 one-hot 행으로 표현한 `O ∈ R^(3×V)`를 만들면 `X=OE`와 수학적으로 같다.
실제 구현은 거대한 one-hot 행렬을 만들지 않고 필요한 행을 조회한다.
lookup은 ID에 대해 미분하는 연산이 아니다. **조회된 테이블 값에 대해 미분**한다.

위 세 위치에서 도착한 gradient를 각각 `g₁, g₂, g₃`라고 하면:

```text
∂L/∂E[2] = g₁ + g₃
∂L/∂E[5] = g₂
```

같은 ID가 반복되면 같은 파라미터 행으로 gradient가 합산된다.
문맥 encoder를 거쳤다면 두 `E[2]`에서 출발했어도 서로 다른 경로의 `g₁`, `g₃`가 돌아올 수 있다.

lookup 경로만 있다면, 어느 입력에서도 조회하지 않은 행에는 그 경로의 데이터 gradient가 없다.
그렇다고 “gradient가 0인 행은 항상 값이 그대로다”라고 일반화하면 안 된다.
optimizer의 momentum·weight decay나 다른 공유 경로가 값에 영향을 줄 수 있다.
예를 들어 입력 테이블을 전체 vocabulary의 MLM 출력 classifier 가중치로도 공유하면, 입력에 없던 행도 출력 softmax 경로에서 gradient를 받는다.
이번 검색 실습에는 이러한 tied MLM 출력 경로가 없다.
PyTorch의 padding gradient 처리와 옵션은 [Embedding 공식 문서](https://docs.pytorch.org/docs/stable/generated/torch.nn.Embedding.html)에서 확인할 수 있다.

**체크포인트:** 질의에 한 번도 나오지 않은 토큰의 행이 검색 학습으로 갱신될 수 있는가?
답: 문서에 등장한다면 가능하다. 아래에서 문서 branch에도 gradient가 흐르는 것을 확인한다.

## 4. 먼저 평균 encoder가 표현할 수 없는 것을 증명하기

padding을 제외한 평균을 계산하고, 학습 가능한 선형층과 L2 정규화를 적용한다.

```text
m = (E[i₁] + ... + E[iₙ]) / n       # 48차원
u = Wm                               # 32차원, projection bias 없음
z = u / ||u||₂                       # 검색 벡터
```

이 모델에서도 토큰 임베딩과 선형층을 검색 목적에 맞게 학습할 수 있다.
하지만 덧셈의 교환법칙 때문에 토큰 순서를 잃는다.

```text
문서 A: alice manages bob
문서 B: bob manages alice
```

두 문장의 토큰 multiset이 같으므로 `m_A=m_B`이고, 이후 어떤 공유 선형층을 적용해도 `z_A=z_B`다.
학습량이나 epoch를 늘려도 이 구조적 한계는 해결되지 않는다.
온톨로지로 쓰면 `(alice, manages, bob)`과 `(bob, manages, alice)`를 구별하지 못하는 것이다.

그렇다고 모든 주어·목적어 역전 문장이 같은 bag-of-words라는 뜻은 아니다.
한국어의 `철수가 영희를`과 `영희가 철수를`는 공백 토큰 자체가 다르다.
구조 한계를 검증할 때는 **토큰 multiset이 실제로 같은 최소쌍**을 만들어야 한다.

평균 모델의 후속 loss를 `L`이라 할 때, 같은 문장 내 각 비padding 위치에는 평균 연산을 통해 동일한 `1/n` 비율의 gradient가 분배된다.
여러 문장에 참여한 토큰은 그 문장들에서 온 서로 다른 gradient를 합산한다.
이 모델도 빈도와 감독 신호에 따라 의미 있는 검색 표현을 학습할 수 있지만, 순서 구분 능력은 생기지 않는다.

**체크포인트:** 평균 다음에 비선형 MLP를 두면 A와 B를 구별할 수 있을까?
답: 없다. 동일한 평균 벡터를 받은 결정적 함수는 동일한 출력을 만든다.

## 5. 문맥 encoder를 직접 구성하는 이유

이번 두 번째 모델은 학습 가능한 위치 벡터를 더하고 입력 LayerNorm을 적용한 뒤, 양방향 Transformer block 두 개를 통과한다.
토큰 차원은 48, head 수는 4이므로 각 head의 차원은 12다.

```text
H₀[t] = LayerNorm(E[id_t] + P[t])
Q = HW_Q + b_Q,  K = HW_K + b_K,  V = HW_V + b_V
A = softmax(QKᵀ / √12 + padding_mask)
head_output = AV
```

softmax는 각 query 위치에서 key 위치들을 따라 적용된다.
head별 결과를 이어 붙여 출력 projection을 통과시킨다.
여기서 `V`는 value 행렬이며 vocabulary 크기 기호와 문맥으로 구분한다.
양방향이므로 미래 위치를 차단하는 causal mask는 쓰지 않는다.

각 block은 residual connection과 Post-LayerNorm을 사용한다.

```text
H' = LayerNorm(H + MultiHeadAttention(H))
H_next = LayerNorm(H' + FFN(H'))
FFN(x) = W₂ GELU(W₁x + b₁) + b₂
```

dropout은 0이다. 작은 실습에서 연산과 전후 비교를 명확하게 보기 위한 설정이다.
최종 토큰 출력은 masked mean → 48에서 32로 projection → L2 정규화를 거쳐 검색 벡터가 된다.
질의와 문서는 동일한 encoder 파라미터를 공유한다.

위치 표현이 있으므로 `alice`가 첫 번째인지 세 번째인지에 따라 초기 hidden state가 달라진다.
attention과 FFN은 이를 이용해 순서와 문맥에 따른 표현을 학습할 수 있다.
**학습할 수 있는 구조라는 사실과, 주어진 데이터로 그 규칙을 일반화했다는 사실은 다르다.**

위치 표현이 없는 self-attention stack은 일반적으로 토큰 순열에 대해 equivariant하다.
그 뒤에 순열 불변 mean pooling을 적용하면 순서가 다른 같은 multiset을 구분하지 못한다.
위치 표현을 더한 입력을 곧바로 평균내기만 해도, 같은 길이에서는 토큰합과 위치합이 각각 같아져 충분하지 않다.
순서를 구분하려면 토큰과 위치 정보를 단순 덧셈 이상으로 결합해야 한다.
이번 모델에서는 attention과 FFN이 그 결합을 학습한다.

역전파는 최종 벡터에서 pooling, FFN, attention, 위치 테이블, 토큰 테이블까지 이어진다.
attention에서는 query·key·value 경로 모두 학습에 참여한다.
attention weight 한 장만 보고 “모델이 이 토큰 때문에 판단했다”고 단정할 수는 없다.

이 모델은 BERT와 핵심 encoder 연산을 공유하는 작은 학습용 모델이다.
원형 BERT의 WordPiece, token-type 입력, MLM·NSP 사전학습, 모델 크기를 재현하지 않는다.
원형 BERT는 입력 토큰·위치·segment 표현과 양방향 Transformer를 사용하고 MLM·NSP로 사전학습했다. [BERT 원논문](https://aclanthology.org/N19-1423/)

## 6. 검색 loss가 어느 방향으로 벡터를 바꾸는가

한 질의 `q`와 12개 후보 문서 `d₁…d₁₂`를 각각 독립적으로 인코딩한다.
이 실습은 질의당 정답 문서 하나를 지정하고 나머지 문서를 negative로 취급한다.

```text
z_q = encoder(q), z_j = encoder(d_j)
s_j = z_qᵀ z_j                       # 정규화되어 있으므로 cosine
ℓ_j = s_j / τ, τ = 0.1
p_j = exp(ℓ_j) / Σ_k exp(ℓ_k)
L = -log p_positive
```

두 입력을 독립적으로 벡터화하므로 문서 벡터를 미리 계산해 검색에 사용할 수 있다.
질의·문서 encoder와 관련성 학습이라는 설계는 [DPR 원논문](https://aclanthology.org/2020.emnlp-main.550/)으로 연결된다.
이번 실습의 공유 파라미터·평균 pooling·정규화 점수를 DPR 원형의 설정과 동일시하지는 않는다.

정답을 표시하는 one-hot 값을 `y_j`라 하면:

```text
∂L/∂ℓ_j = p_j - y_j
∂L/∂s_j = (p_j - y_j) / τ
∂L/∂z_q = (Σ_j p_j z_j - z_positive) / τ
∂L/∂z_j = (p_j - y_j) z_q / τ
```

첫 줄은 **logit** 미분이고 두 번째는 온도로 나누기 전 **유사도** 미분이다.
배치 평균 loss를 쓰면 각 질의의 기여에는 추가로 배치 크기의 역수가 곱해진다.
정답 점수가 낮으면 정답의 점수를 올리는 방향, 오답 확률이 크면 해당 오답 점수를 내리는 방향의 신호가 커진다.
다만 파라미터가 공유되므로 실제 update 후 모든 개별 점수가 동시에 원하는 만큼 움직인다는 보장은 없다.

예를 들어 세 후보에서 `p=[0.2, 0.5, 0.3]`, 첫 후보가 정답이고 `τ=0.1`이라면:

```text
∂L/∂s = [-8, 5, 3]
```

gradient descent는 loss를 줄이므로 첫 점수를 올리고 두 번째·세 번째 점수를 내리려 한다.
온도를 바꾸면 `1/τ` 배율뿐 아니라 `p` 자체도 바뀐다. 온도는 단순한 learning-rate 배수가 아니다.
L2 정규화가 있으므로 전체 벡터 크기를 키우는 것만으로 cosine 점수를 높일 수 없다.

정규화 전 벡터가 `u`, 정규화 후가 `z=u/||u||`일 때:

```text
∂L/∂u = (I - zzᵀ) / ||u|| × ∂L/∂z
```

이는 `||u||`가 0이 아니고 구현의 epsilon clamp가 활성화되지 않은 영역의 식이다.
`I-zzᵀ`는 현재 벡터 방향 성분을 제거한다. 정규화 때문에 주로 방향을 바꾸는 신호가 이전 층으로 전달된다.
gradient의 크기에는 정규화 전 norm도 영향을 준다.

문서 쪽 식에도 gradient가 존재한다는 점을 놓치지 말자.
질의에 없는 `manages`가 문서에 있다면 문서 encoder 경로를 통해 그 임베딩이 학습될 수 있다.
정답 문서뿐 아니라 모든 negative 문서도 loss에 참여한다.
양 branch가 같은 테이블을 쓰므로 동일 토큰 행에는 질의와 문서의 기여가 합산된다.

## 7. 온톨로지를 학습 신호로 바꾸는 법

온톨로지의 entity·관계·타입은 데이터와 평가의 구조를 설계하는 데 사용할 수 있다.
임베딩의 7번 좌표를 `is-a`, 12번 좌표를 `part-of`로 수동 지정할 필요는 없다.

cosine 공간의 모든 벡터에 같은 직교변환 `R`을 적용하면:

```text
(Rz_q)ᵀ(Rz_d) = z_qᵀRᵀRz_d = z_qᵀz_d
```

검색 점수가 그대로이므로 loss만으로 각 좌표에 유일한 의미가 정해지지 않는다.
이 주장은 검색 출력 공간의 점수 불변성이다. 모든 내부 층을 임의로 회전해도 동일 모델이라는 뜻은 아니다.
입력 토큰끼리의 최근접 이웃이 곧 검색 품질을 설명하는 것도 아니다. 중간 encoder가 표현을 변환하기 때문이다.

| 온톨로지 정보 | 데이터로 바꾸는 예 | 주의점 |
|---|---|---|
| 동의 표현 | `심근경색` 질의와 `급성 심근 경색증` 문서를 연결 | 문맥·범위가 같은 표현인지 확인 |
| 타입 계층 | 상위 개념 질의에 여러 하위 개념 문서를 positive로 지정 | 상위·하위를 항상 동일 벡터로 강제하지 않음 |
| 방향 관계 | `A manages B`와 `B manages A`를 최소쌍으로 생성 | 역관계가 실제로 틀린 답인지 확인 |
| 역할 | 같은 entity가 치료제·원인·증상 역할로 등장하도록 구성 | 단어 동시출현만으로 정답이 결정되지 않게 함 |

ontology가 정의한 사실과 검색의 관련성 판정 사이에는 별도 정책이 필요하다.
예를 들어 “포유류의 예”에는 고래와 개가 모두 정답일 수 있다.
고래만 positive로 두고 개를 negative로 두면 같은 ontology가 제공한 정답끼리 밀어내게 된다.

multiple positives의 한 가지 loss는 다음과 같다.

```text
L = -log [Σ_{p∈P(q)} exp(s_p/τ) / Σ_{j∈C(q)} exp(s_j/τ)]
```

이 loss는 정답 집합의 총확률을 높이지만 모든 정답을 균등하게 잘 찾도록 강제하지는 않는다.
모든 positive를 충분히 올려야 한다면 positive별 loss 평균 같은 별도 목적을 검토한다.
이번 단일 정답 실습에 이 변경을 자동으로 적용하지 말고, 먼저 relevance label을 다시 설계해야 한다.

hard negative는 모델이 높게 점수화하지만 실제로는 정답이 아닌 문서다.
단어가 겹치는 관계 역전 문서는 좋은 후보지만, label 검토 없이 선정하면 false negative가 된다.
큰 corpus에서는 전체 문서 대신 in-batch·샘플링·검색 기반 negative를 쓰며, negative의 분포도 학습 결과에 영향을 준다.

## 8. 결과를 읽고 다음 설계로 연결하기

실습에서는 다음 증거를 연결해서 해석한다.

1. lookup과 one-hot 행렬곱이 같은 값을 내는지 확인한다.
2. 반복 ID의 gradient가 합산되고 padding 처리가 유지되는지 확인한다.
3. 평균 encoder에서 같은 multiset의 관계 역전 문서가 같은 벡터가 되는지 확인한다.
4. 문맥 encoder가 해당 최소쌍을 구분할 수 있는지 학습 결과로 확인한다.
5. train과 validation의 검색 순위 및 Recall@k·MRR을 함께 읽는다.

질의당 정답이 하나라면 Recall@k는 정답이 상위 k개에 들어간 질의의 비율이다.
MRR은 각 질의에서 정답 순위의 역수 `1/rank`를 평균낸 값이다.
아주 작은 고정 corpus에서 높은 점수가 나와도 실제 한국어 검색의 성능 근거가 되지는 않는다.

validation은 파라미터 update에 쓰지 않더라도 설계와 hyperparameter를 선택하는 데 쓰면 선택 과정에 참여한다.
최종 일반화 주장은 별도 test set으로 확인한다.
특히 질문 문구만 바꾼 분할, 새로운 entity 분할, 새로운 관계 조합 분할을 구분한다.
온톨로지 템플릿에서 생성한 문장이 서로 다른 split에 거의 그대로 반복되면 암기 효과를 과대평가하기 쉽다.

모델을 학습한 뒤에는 vocabulary·토큰화 규칙·encoder·projection·정규화를 하나의 버전으로 저장한다.
encoder를 바꾸면 기존 문서 벡터도 다시 계산해야 한다.
문서 벡터를 고정한 채 질의 encoder만 학습하는 것은 가능하지만, 이번 양쪽 branch 학습과는 다른 설계다.
현재 12개 문서는 정확한 전체 점수 계산으로 충분하다. ANN 인덱스는 큰 corpus에서 추가하는 별도 근사화 단계다.

**마지막 체크포인트:** 다음 문장을 자신의 말로 설명하면 이번 단계를 이해한 것이다.

> 토큰 임베딩의 각 행은 단독으로 의미를 부여받는 게 아니라, 검색 label이 만든 오차가 공유 encoder를 통과해 돌아오면서 바뀐다. 무엇을 구별할 수 있는지는 토큰화와 구조가 정하고, 실제로 무엇을 구별하게 되는지는 데이터와 loss가 정한다.
